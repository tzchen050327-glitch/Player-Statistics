# Supabase Data API and function permissions (2026-10-21)

Production project: **CPBL Player Stats** (`kjndnsztbcpmkhictjkr`).

## Applied to production on 2026-10-21

Supabase migrations:
- `tighten_public_data_api_privileges_20261021`: removed anon/authenticated write grants from existing public tables (there were **zero** public RLS write policies), restricted 4 mutating SECURITY DEFINER RPCs and 8 trigger functions to the server-side role, and removed `postgres` default table/sequence privileges for new public objects.
- `pin_public_function_search_paths_20261021`: fixed search paths for 33 public functions (`pg_catalog, public, extensions, pg_temp`).

Validation after deployment: all 54 current public tables retain service_role SELECT; 23 preserve anon SELECT; anonymous INSERT grants went from 21 to 0. Remaining two publicly callable SECURITY DEFINER RPCs (`matchup_h2h`, `matchup_recent6`) are intentionally retained for read-only matchup queries.

**Do not blindly re-run these migrations or re-enable default anon table grants.** Restore from Supabase migration history and review actual SQL before applying to another environment.

## Every new table must declare its Data API contract

Beginning 2026-10-30, Supabase requires explicit grants on newly created public tables. The production `postgres` default privileges were already changed on 2026-10-21, so explicit grants are required now for tables it creates.

### Backend-only table

```sql
create table public.example_backend_cache (
  id bigint generated by default as identity primary key,
  payload jsonb
);
alter table public.example_backend_cache enable row level security;
revoke all on public.example_backend_cache from anon, authenticated;
grant select, insert, update, delete on public.example_backend_cache to service_role;
-- Grant sequence USAGE to service_role if an identity/default sequence requires it.
-- Do not create an anon/authenticated policy or grant for backend-only state.
```

### Public read-only table

```sql
create table public.example_public_scores (
  id bigint generated by default as identity primary key,
  score jsonb not null
);
alter table public.example_public_scores enable row level security;
create policy example_public_scores_read on public.example_public_scores
  for select to anon, authenticated using (true);
grant select on public.example_public_scores to anon, authenticated;
grant select, insert, update, delete on public.example_public_scores to service_role;
```

Never put `service_role` credentials in the frontend. Do not grant writes to `anon` or `authenticated` without a reviewed, restrictive write policy.

## Pre-deployment checks

1. Inventory all new public tables and explicit grants, including required sequence privileges.
2. Confirm public tables have RLS, check every RLS policy, and ensure `service_role` receives the required explicit grants.
3. Verify that backend Edge Functions and cron jobs still read/write expected caches.
4. Re-run Supabase Security Advisor after schema/function changes.
5. Do not grant SECURITY DEFINER functions to PUBLIC automatically. Explicitly allow read-only public RPCs only after checking their output and arguments.
6. Check `pg_default_acl` ownership. The `postgres` defaults are restricted; `supabase_admin` had separate historical defaults, which cannot be altered through the connected `postgres` session. Do not assume all creator roles share the same defaults.

Useful checks:
```sql
select pg_get_userbyid(defaclrole) as object_creator,
       defaclobjtype, defaclacl
from pg_default_acl
where defaclnamespace = 'public'::regnamespace;

select n.nspname as schema_name, c.relname as table_name, c.relrowsecurity as rls_enabled,
       has_table_privilege('anon', c.oid, 'SELECT') as anon_can_select,
       has_table_privilege('anon', c.oid, 'INSERT') as anon_can_insert,
       has_table_privilege('service_role', c.oid, 'SELECT') as service_can_select
from pg_class c
join pg_namespace n on n.oid = c.relnamespace
where n.nspname='public' and c.relkind in ('r','p')
order by c.relname;
```
